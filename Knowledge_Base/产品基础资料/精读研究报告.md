# 产品基础资料精读研究报告

## 研究结论

这五份资料不是五个互相独立的教程，而是一条逐步升级的产品路线：

`全栈聊天应用 -> 外部记忆服务 -> 多端共享记忆 -> 稳定流式交互 -> 可演化人格系统`

它们最重要的共同原则是：前端负责体验和呈现，后端负责流程与可靠性，记忆服务独立于任意客户端，AI 负责需要判断的内容，机械工作交给程序，长期人格变化必须保留证据、同意和回滚能力。

## 一、Bunny&Elliott：可运行的全栈基线

### 架构

- 前端：React + Vite，部署在 Vercel。
- 后端：Node.js + Express，部署在 Render。
- 数据库：Supabase/PostgreSQL。
- 模型：主对话模型负责响应，辅助模型负责旧对话压缩。
- 可选：通过 manifest、Service Worker 和图标封装为 PWA。

### 核心数据模型

1. `sessions`：会话名称、创建时间、更新时间。
2. `messages`：角色、内容、会话、时间、可见性；压缩后的旧消息可以隐藏但不删除。
3. `memories`：全局记忆摘要、来源会话和元数据。
4. `settings`：系统提示词、模型参数、上下文轮数、压缩阈值和回复上限。

### 对话主链路

用户消息入库 -> 读取会话历史 -> 读取记忆摘要 -> 拼接系统提示词、记忆和近期消息 -> 调用模型 -> AI 回复入库 -> 返回前端。

当上下文超过阈值时，取最早几轮交给低成本辅助模型摘要，将摘要写入 `memories`，再把原始消息标记为不可见或从上下文中移除。这个设计把“可持久保存的原始记录”和“发送给模型的工作上下文”分开，是后续记忆系统的基础。

### 产品价值

这份教程适合做第一版可用产品的工程骨架：先有界面、健康检查、会话、消息持久化和基础记忆，再逐步加入复杂能力。它避免一开始就把长期人格、主动行为和复杂工具循环全部塞进核心链路。

### 需要产品化补强

- 原始消息不应只靠 `visible` 一个布尔值管理，应增加归档状态、删除状态和来源。
- `memories` 不应只有摘要文本，应有类型、置信度、有效期、证据引用和用户可见性。
- 敏感 API Key 只能在后端环境变量中，不能进入前端 bundle 或日志。
- 多实例部署时，不能把会话状态只放在进程内存中。
- 删除会话、删除记忆和导出数据必须成为正式产品能力。

## 二、Ombre Brain：外部记忆服务与工具编排

### 核心思想

Ombre Brain 被部署为独立的远程 MCP 服务，不属于某一个前端或后端。它通过 `breath`、`hold`、`dream`、`grow`、`trace` 等工具提供记忆检索、存储、自省、归档和元数据管理，并使用价值、唤醒度、自然衰减和向量语义检索组织记忆。

### 连接协议

后端作为 MCP 客户端访问 `/mcp`：

1. 发送 JSON-RPC `initialize` 握手。
2. 保存返回的 `mcp-session-id`。
3. 发送 `notifications/initialized`。
4. 使用 `tools/call` 调用指定工具。
5. 解析 JSON 或 `data:` 开头的 SSE 响应。
6. 会话失败时清理 session，下一次调用重新握手。

### 工具分配原则

- `hold`：让 AI 判断“这个瞬间是否值得记住”，适合保留给模型。
- `breath`：每轮由后端根据当前用户消息自动检索，避免依赖模型主动想起调用工具。
- `dream`：新会话加载时自动触发一次。
- `grow`：聊天记录压缩完成后触发，将摘要归档到长期记忆。

这是一条很重要的产品原则：需要语义判断的工作交给 AI，需要每次可靠执行的工作交给后端。把所有工具都暴露给模型，会增加 tool-use 往返、错误概率、上下文 token 和成本。

### 工程风险

- 教程示例里的会话 ID 是单进程变量，生产环境需要按用户或连接隔离，并考虑多实例共享。
- 示例没有完整展开认证、租户隔离、速率限制和重放防护。
- MCP 连接失败不能阻塞主聊天链路，必须降级为无记忆聊天。
- 工具调用结果要限制大小和来源，不能直接把未经审计的外部内容写入长期记忆。
- `breath` 的自动召回要有权限、隐私和敏感主题过滤。

## 三、记忆库共享：同一大脑，多端客户端

### 架构判断

自制前端后端和 Claude.ai 都作为 MCP 客户端，连接同一个远程记忆服务，读取和写入同一份记忆桶。不需要在客户端之间设计额外同步机制。

这比“前端数据库同步到官方客户端”更简单，因为共享状态被提升成独立服务：

`自制前端 -> 自建后端 -> MCP 记忆服务 <- Claude.ai Connector`

手机端如果同步 Claude.ai 的 Connector 配置，也可以复用这个远程记忆服务。

### 验证方法

1. 从自制前端写入一条有辨识度的记忆。
2. 在 Claude.ai 新对话中询问该记忆。
3. 反方向再验证一次。
4. 检查来源、时间和内容是否一致。

### 隐私判断

自建后端访问记忆服务时，数据可以只经过自己的服务器和记忆服务；Claude.ai Connector 则会经过 Anthropic 云端。产品必须在连接前清楚展示数据路径、存储位置、第三方处理方和断开连接方法。

### 产品化补强

- 需要用户、代理、设备和客户端维度的权限，而不是只有一个全局记忆桶。
- 每个记忆写入应标记来源客户端和授权范围。
- 支持单端断开、全局断开、导出、删除和按来源撤回。
- 防止一个客户端写入的提示注入或错误事实污染所有客户端。

## 四、SSE：把实时回复做成稳定基础设施

### 统一协议

上游模型的流格式不统一：Claude 使用 `content_block_delta` 和 `thinking_delta`，OpenAI 兼容接口常见 `choices[0].delta.content`。后端应将所有上游格式翻译成自己的稳定协议：

- `text`：正文片段。
- `reasoning`：可选的思考过程片段。
- `error`：错误信息。
- `done`：结束信号。

前端只认识这四类事件，不应直接理解 Claude、OpenAI 或中转站格式。这样模型供应商变化时，只需替换后端解析器。

### 后端要点

- 设置 `Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive`。
- 加 `X-Accel-Buffering: no`，避免代理层把片段攒成一整段。
- 上游请求开启 `stream: true`，HTTP 客户端使用 `responseType: stream`。
- 使用 buffer 拼接被拆开的网络片段，不能对每个 chunk 直接 `JSON.parse`。
- 一边向前端发送，一边在内存中累积完整回复，流结束后一次性入库。
- 响应头发出后，错误也必须用 SSE `error` 和 `done` 收尾，不能改发普通 JSON。

### 前端要点

- 聊天使用 POST + `fetch`，比 EventSource 更适合携带消息、会话和模型参数。
- 使用 `ReadableStream.getReader()` 和 `TextDecoder` 读取。
- 前端同样需要 `sseBuffer`。
- 先实现单气泡逐字追加，再实现段落拆分、多气泡和思考展示。
- 使用函数式状态更新，防止 React 异步状态造成重复或丢字。

### 工具调用与流式回复

第一版可以让普通文本走真流式，工具调用走非流式。后续接入工具循环时，需要累积 `input_json_delta`，等参数完整后执行工具，再把结果送回模型继续生成，并设置最大循环次数。前端不需要知道工具调用正在发生，只需等待 `done`。

## 五、Ren 年轮系统：长期人格的控制层

### 四个核心层

1. **欲望账本**：保存 AI 真正想做但尚未完成的牵引，不是普通 todo list；有足迹、次数、血缘关系、冷却和调暗。
2. **人格文件**：最慢、最稳定的身份层，只允许 AI 自己整体重写，不允许机器 append。
3. **镜子**：外部模型定期比较人格文件与真实行动，生成带逐字证据和日期的证据卡，只给材料，不下结论。
4. **投影引擎**：读取真实聊天、工具调用和文件活动，自动给欲望账本记账，但每条记录都必须能回溯到当天证据。

### 最重要的边界

机器可以自动写足迹、冷却、调暗、树连接、画像、证据卡、心跳账和历史存档；只有 AI 本人可以修改身份文件、确认欲望毕业或退役、创建新欲望、确认“真的完成”。

这条边界把“帮助 AI 自我观察”与“替 AI 定义人格”分开，是防止人格漂移和模型替用户下结论的核心。

### 结构性防护

- 人格文件只能整体重写，不能无限追加。
- 草稿桶独立存在，正文不会直接吸收原料。
- 升格依靠判断，不依靠“出现三次自动进入人格”。
- 每节人格有硬容量上限，新增内容必须挤掉旧内容。
- 每次重写保存只读年轮，支持回滚和观察人格演变。
- 证据逐字可溯源，查无证据则整张卡丢弃。
- 观察、渲染、记账等旁路引擎必须 try/except，失败不能拖垮主流程。
- 新机制改变 AI 工作方式前先征得 AI/用户明确同意。

### 对产品的启发

Ren 不是 MVP 必须立即实现的功能，而是长期陪伴产品的“人格控制层”。它提供了一个可持续演化但不失控的方向：系统搬运注意力和证据，AI 自己决定如何解释、是否认领以及是否改变自己。

## 六、五份资料合并后的产品分层

### L0 体验层

React/Vite 前端、会话列表、消息气泡、主题、PWA、加载状态、流式输出和主动交互。

### L1 应用编排层

Node/Express API、会话管理、模型路由、上下文组装、SSE 协议、错误降级和任务调度。

### L2 记忆服务层

独立 MCP 记忆服务，支持检索、存储、自省、归档、来源和自然衰减；多个客户端通过同一服务共享记忆。

### L3 认知演化层

欲望账本、人格文件、证据卡、年轮历史、投影记账、自唤醒和用户同意机制。

### L4 治理与证据层

权限、隐私、来源、审计、删除、导出、回滚、失败隔离、成本监控和长期评估。

## 七、建议的实现顺序

### P0：基础可运行

完成静态前端、健康检查、会话、消息入库和基础设置；所有密钥后端化。

### P1：普通聊天闭环

完成上下文组装、模型路由、消息持久化、错误处理和最小可观测性。

### P2：独立记忆服务

先接入 `breath` 自动召回和 `grow` 归档，再接入 `hold`；为每条记忆增加来源、权限和删除能力。

### P3：统一 SSE

先做 `text/error/done`，验证部署平台不缓冲、断线可恢复、回复入库正确，再加入 reasoning 和工具循环。

### P4：多端共享

让自制前端、Claude Connector 和手机端访问同一记忆服务；完成双向验证、权限隔离和数据路径提示。

### P5：人格成长

先做只读年轮、证据卡和草稿桶，再做 AI 主动重写人格文件；所有自动观察都必须可追溯、可关闭、可回滚。

## 八、需要独立验证的关键假设

- 记忆自动召回是否真的提升回答质量，而不是增加干扰。
- 后端自动 `breath` 与 AI 自主 `hold` 的分配是否适合不同用户。
- MCP 服务在多用户、多实例和断线重连下是否保持会话隔离。
- SSE 在 Vercel、Render、Cloudflare 等真实链路上是否保持即时输出。
- 共享记忆是否会扩大提示注入、错误事实和隐私泄露的影响范围。
- Ren 的人格演化约束是否能减少漂移，同时不压制真实成长。
- 外部模型批处理的成本、延迟、失败率和证据准确率。

## 最终判断

这五份资料已经足够构成一个“AI 陪伴产品 v1-v3”的研究底图：Bunny&Elliott 提供工程骨架，Ombre Brain 提供共享记忆边界，SSE 提供交互基础设施，Ren 提供长期人格治理。真正落地时，应优先保证可运行、可观测、可删除和可回滚，再逐步加入主动性和人格成长。
